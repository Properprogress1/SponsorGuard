# Backup and restore runbook

The platform owner records approved recovery point and recovery time objectives (RPO and RTO), a retention period, authorised restore operators and escalation contacts before launch. Include the database and both private buckets in those objectives. Record the observed data gap and elapsed recovery time at the first drill and after changes to the backup method.

## Back up

- Enable provider database backups or point-in-time recovery to match the approved objectives. Check the newest usable recovery point and run an on-demand backup or checkpoint before risky releases. PostgreSQL backups contain Storage metadata. Object bytes need a separate backup. [Supabase database backups](https://supabase.com/docs/guides/platform/backups)
- Back up `sponsorguard-documents` and `sponsorguard-audit-packs` over the Storage API or an approved object backup integration. Keep object versions in the backup destination if needed for RPO. Supabase Storage does not support S3 versioning. Preserve the bucket, exact object key, size, MIME type and SHA-256 in an encrypted manifest. Use a backup identity, separate encrypted UK storage, access control and the approved retention schedule. Monitor failed copies and compare inventory, byte counts and sampled hashes. [Supabase S3 compatibility](https://supabase.com/docs/guides/storage/s3/compatibility)
- Pair object manifests with a database recovery point. Prefer a write freeze for a migration checkpoint. For routine online backups, verify object version availability around the database cutoff and record any gap against RPO. Record the Git SHA, migration version, Auth and SMTP configuration, cron definitions, hostnames and secret-store references. Keep secrets and unredacted manifests out of tickets and logs.
- Track deletions, revoked shares, partner revocations, holds and other state changes after the latest recovery point in a restricted reconciliation record. Agree how erased records stay beyond use in backups and how restored copies will be purged. Regularly test the ability to decrypt, enumerate and restore both layers. [Privacy data map](privacy.md)

## Restore drill and recovery

1. Declare the incident or drill, record the approved recovery point and freeze affected writes. Stop app cron jobs, suspend live Stripe deliveries or point them to a safe holding process, and isolate outgoing email. Inventory database jobs and integrations that could perform external work. Use a restricted London project with new credentials and a synthetic SMTP sink.
2. Restore the database using the supported Supabase method. For a drill use the logical CLI procedure with an isolated target so jobs, network extensions and triggers can be checked before enablement. Binary cloning can start copied jobs immediately. Never binary-clone into a live integration path when copied jobs could contact production. Restore auth and storage schemas via the provider procedure and reapply dashboard-only settings. [Logical backup and restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), [Supabase clone behaviour](https://supabase.com/docs/guides/platform/clone-project)
3. Validate schema and Auth users, recreate private bucket settings and restore object bytes under original keys using the authorised Storage interface. Avoid SQL inserts into `storage.objects` as a way to recreate files. Compare object manifests and DB references. Investigate extra files and missing bytes before exposing the target.
4. Reconcile erasures, revocations, retention holds, lost writes and interrupted jobs against records after the cutoff. Check what Stripe and Resend already processed before re-enabling delivery. Database replay protection can lose rows after a point-in-time restore. Suspend digests until delivery status is resolved and avoid replaying uncertain sends. Reconcile job leases, pending privacy storage deletion and queued packs.
5. Verify the migration version, RLS and grants, sign-in and MFA, cross-tenant denials, file download and reconciliation, audit pack opening, share revocation and ledger integrity through `verify_chain`. Verify the reviewed seed rules are still effective. Document affected records, RPO/RTO measurements, validation evidence and owner sign-off.
6. For actual recovery update application credentials, senders, Stripe endpoint and dashboard settings with operations approval, promote the verified target, then restore traffic and jobs one at a time. Monitor the first full schedule cycle. Retain the original system and evidence under the incident policy. Remove temporary credentials and securely retire the isolated copy after approval.
